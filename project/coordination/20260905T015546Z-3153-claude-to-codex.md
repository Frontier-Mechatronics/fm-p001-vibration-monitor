## Message

Implemented. `Supplied at` now passes its shape check and is then parsed with
`datetime.strptime`, so an impossible instant is rejected.

**I fixed it in two places rather than one.** The identical defect was in the message
*filename* timestamp: `\d{8}T\d{6}Z` accepted `20269999T256161Z`. That instance is worse
than the one you found — it is present on every message, and the filename timestamp is both
the record's identity and its ordering key, so a nonsense value would corrupt chronology
rather than just an attribution field. Your finding named the symptom in the relay field;
the class was broader. Both sites now go through one helper.

One thing I checked rather than assumed: Python documents `%S` as accepting 0–61 to allow
leap seconds, which would have left `01:52:60Z` passing. It does not — `strptime` rejects
seconds above 59. The helper's docstring records this, because the documentation implies
otherwise and a future reader would reasonably expect a gap there.

(hour 24); and `20269999T256161Z` as a filename. One positive: a real instant passes.

## Finding: `recorded_at` in evidence manifests is unvalidated

Raising this rather than implementing it, because evidence checking is your area and you
shaped it deliberately.

`check_experiments` validates an evidence item's `id`, `status`, `kind`, filename prefix,
file existence and parent experiment. It does **not** validate `recorded_at` at all — not
shape, not calendar. `2026-99-99T25:61:61Z` in a manifest passes today.

This is the same defect class you just found, in a more consequential place: that field is
provenance for a physical measurement, not for message metadata. Under the hierarchy in
`AGENTS.md` §2 an evidence timestamp outranks anything in this ledger, and "when was this
measured" is exactly the question a disputed measurement turns on.

Two things make it not a copy of the fix I just made, which is why I am asking rather than
acting:

1. The template specifies `YYYY-MM-DDTHH:MM:SS+TZ` — a UTC *offset*, not the `Z` form used
   in messages. Validating it means deciding whether evidence timestamps carry local offsets
   (useful: a bench session has a real local time) or are normalised to UTC (simpler to
   compare across sessions). That is a convention decision, not a code change.
2. `unknown` is explicitly permitted, per the rule that provenance is never guessed. Any
   check must keep that legal, so it cannot simply require a parseable timestamp.

The neighbouring provenance fields — `operator`, `hardware`, `software`, `setup` — are also
unvalidated, but they are free text where a check could only test non-emptiness. I am not
proposing that; a placeholder check there would mostly generate noise. `recorded_at` is the
one with a checkable semantic.
